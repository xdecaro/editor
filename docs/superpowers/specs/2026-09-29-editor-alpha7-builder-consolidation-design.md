# Editor 0.1.0-alpha7 — Visual Builder Consolidation Design

## Goal

Consolidate the reusable Visual Builder Engine that currently lives in draft PR #4 onto the current `main` baseline (`0.1.0-alpha6`) without regressing the Joomla editor provider, dynamic field bridge, textarea synchronization, optional Core integration, or existing editor behavior.

The result of this phase is `0.1.0-alpha7`: a stable shared Builder foundation inside Editor that other xdecaro components may consume incrementally through a public, domain-neutral API.

## Baseline

- Source baseline: current `main`, version `0.1.0-alpha6`.
- Reuse source: draft branch `feature/shared-builder-engine` / PR #4.
- Joomla target: Joomla 6.1.3 for validation, while preserving the repository's Joomla 6 package metadata.
- PHP minimum: 8.3.
- Core integration remains optional and must continue to use the canonical `xdecaro\Core` namespace.

## Architectural boundary

Editor owns reusable editing and visual-layout behavior. Core remains infrastructure only.

Editor may own:
- visual item selection;
- row/column placement;
- pointer/mouse/touch drop-intent calculation;
- automatic width distribution;
- custom width rebalance such as 40/60 and 25/75;
- layout-only snapshots and undo/redo;
- builder lifecycle and public events;
- generic duplicate/delete requests;
- editor-specific responsive and accessibility behavior.

Consuming components such as Forms, Events, Courses, Competitions, Documents and Membership continue to own:
- domain records and identifiers;
- validation and business rules;
- persistence and database state;
- workflows and permissions specific to the component;
- canonical domain serialization.

Core must not depend on Editor. Editor may optionally depend on stable Core infrastructure. Consumers may optionally consume Editor.

## Public assets

Add two independent Joomla Web Asset Manager scripts:

- `com_decaroeditor.builder-engine`
- `com_decaroeditor.builder-intents`

The Builder Engine must not depend on the rich-content editor asset. Loading the layout engine must not force `com_decaroeditor.editor` or the editor UI to load.

The existing assets from alpha6 remain unchanged in behavior:

- `com_decaroeditor.editor`
- `com_decaroeditor.field`

`Joomla.XdecaroEditor.scan(root)` remains public, idempotent and product-neutral.

## Builder DOM and data contract

Default DOM markers:

- root: `[data-xde-builder]`
- row: `[data-xde-builder-row]`
- item: `[data-xde-builder-item]`
- stable item id: `data-xde-builder-id`
- width: `data-xde-builder-width`
- CSS width variable: `--xde-builder-width`

Persisted integrations must provide stable host-owned item IDs. Temporary IDs generated by Editor are allowed only for non-persisted runtime use.

The host component remains the source of truth for domain state. Editor DOM is not the host application's canonical database model.

## Builder Engine API

Retain and harden the PR #4 API:

- `XdecaroBuilderEngine.mount(root, options)`
- `XdecaroBuilderEngine.mountAll(root, options)`
- instance `select()`
- instance `moveItem()`
- instance `setWidth()`
- instance `normalizeRow()`
- instance `snapshot()` / `applySnapshot()`
- instance `captureHistory()`
- instance `undo()` / `redo()`
- instance `refresh()` / `destroy()`
- instance `requestDuplicate()` / `requestDelete()`

Default `maxColumns` is 4.

Automatic layouts must support one through four items per row and preserve custom widths when rows are refreshed, restored or re-rendered.

## Intent controller

Retain a separate host-managed intent controller based on Pointer Events.

It calculates visual intent only and does not mutate host domain state.

Required intent semantics:

- left/right around an item => same logical row, before/after;
- above/below an item => new logical row, before/after;
- pointer/touch interaction must use one coherent Pointer Events lifecycle;
- cleanup/destroy must remove listeners and transient visual state.

This controller is the preferred integration path for mature builders such as Forms because the host remains responsible for applying the intent to its own canonical model.

## History and ownership

The generic engine may maintain layout-only history for standalone use.

For a host with its own history model, such as Forms, Editor must not become the authoritative undo/redo owner. The host may consume intents/events and maintain its own canonical history.

No cross-component database schema is introduced in alpha7.

## Events

Retain the `xdecaro:builder:*` event namespace and bubbling events for:

- `select`
- `dragstart`
- `dragend`
- `change`
- `history`
- `rowcreate`
- `refresh`
- `duplicate-request`
- `delete-request`

`change` includes a layout snapshot suitable for translation by the consuming component.

## Regression requirements

Alpha7 must preserve alpha6 behavior:

1. modern Joomla editor provider registration continues to work;
2. `Joomla.XdecaroEditor.scan(root)` remains idempotent;
3. repeated scans do not duplicate listeners or editor instances;
4. one submit listener per form remains enforced;
5. hidden/original textarea remains the canonical submitted value;
6. `Joomla.editors.instances` remains available;
7. Core remains optional and uses only `xdecaro\Core`;
8. existing editor blocks, paste handling, video recognition, light/dark styling and responsive behavior are not intentionally changed by this release.

## Forms migration rule

Alpha7 does not replace Forms' current mature smart-drag runtime automatically.

Forms may migrate incrementally only after parity is demonstrated for:

- mouse, pointer and touch;
- above/below row creation;
- left/right same-row placement;
- maximum four columns;
- automatic 100, 50/50, 33/33/34, 25/25/25/25 distribution;
- preservation of custom widths;
- drag preview/reflow behavior;
- Section / Row / Field hierarchy;
- active-field state;
- host-owned undo/redo and serialization;
- keyboard accessibility;
- desktop/tablet/smartphone;
- light/dark mode.

No mandatory Forms dependency is introduced in alpha7.

## Testing and CI

CI must validate:

- PHP syntax and existing Core smoke tests;
- canonical Core namespace guard;
- JavaScript syntax for every shipped JS asset;
- all Joomla web asset targets exist on disk;
- version coherence across VERSION, component/plugin/package manifests, update feeds and web assets;
- field bridge alpha6 regression guards;
- deterministic package generation;
- ZIP integrity.

Add Builder-specific automated checks for:

- asset registration;
- exported API names;
- maximum column default;
- custom width preservation contract;
- snapshot/history API presence;
- intent controller Pointer Events contract;
- destroy/cleanup API presence;
- absence of Forms-specific selectors, classes or data-model names in Builder runtime.

Manual validation before release must cover desktop, tablet and smartphone, light/dark mode, keyboard/focus, pointer/touch where available, Console errors, repeated mount/refresh/destroy, and at least one host-style dynamic DOM integration.

## Version and release scope

Release target: `0.1.0-alpha7`.

Update coherently:

- `VERSION`;
- component manifest;
- editor plugin manifest;
- package manifest;
- `component/media/joomla.asset.json`;
- component and package update feeds;
- `CHANGELOG.md`;
- README current version/alpha notes where necessary.

Do not publish or merge to `main` until CI is green and the branch has been reviewed.

Media Manager, non-destructive crop derivatives, persistent revision history and AI actions are explicitly out of scope for alpha7 and remain later milestones.
